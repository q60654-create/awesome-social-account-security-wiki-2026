> **Key Takeaway:** When a tdata import spins forever, check three layers in order: is the folder in the directory the client actually reads, does the client version match the session generation, and does the folder allow writes. Working through path, then version, then permission finds the cause faster than reinstalling the client repeatedly.

A tdata import that spins indefinitely means Telegram Desktop found a directory but could not read a usable session from it. Work through **path, then version, then permission** in that order. Most cases resolve at the first layer. Each step below gives a reproducible verification action; finish it before moving to the next layer and do not skip ahead.

## First, identify which layer is spinning

Where the client freezes tells you which layer to inspect. Separate three symptoms before touching any files:

- **Spins at startup, no login screen appears:** the client is reading the local session directory. The problem is path or permission.

- **Login screen appears but keeps loading and will not respond:** the client found the directory but the session is unusable. The problem is usually version mismatch or a session that has already expired server-side.

- **Interface opens but the message list stays blank and spins:** the session loaded. The problem is the network exit or the account state, not tdata itself.

Only the first two are tdata import problems. For the third, troubleshoot network and account state first using the approach in [2FA and login-state management](https://facai.lol/blog/2fa-login-security-session-management-2026). Do not touch the tdata directory in that case, or you risk losing a working session along with it.

## Layer one: path, tdata must sit where the client reads

Telegram Desktop only reads a `tdata` folder inside its own working directory. When the folder is in the wrong place, the client creates an empty directory instead, which shows up as a startup spin or an immediate login prompt.

1. Quit Telegram Desktop completely. Confirm the tray icon is gone and no process remains.

2. Locate the working directory the client actually uses. For the Windows portable build it is the folder containing `Telegram.exe` after extraction. For the installed build it is usually the `Telegram Desktop` folder under the system user directory. Use the real path on your machine as the reference.

3. Check whether a `tdata` folder already exists there. If it does, rename the whole folder as a backup first. Do not delete it outright.

4. Copy the incoming `tdata` folder in as a whole. The level must be `working-directory/tdata/...`, not `working-directory/tdata/tdata/...`. The extra nested level is the most common failure.

5. Start the client again and watch whether it still spins.

**Verification action:** before launching, open the `tdata` folder and confirm it contains multiple files rather than a single folder. If opening it shows only one folder with the same name, the level is nested; go back one step and redo the copy.

One more caution: do not use the same tdata on multiple devices at the same time. Concurrent reads of a session file can trigger server-side risk controls, which show up as limited functionality after login. When you need isolated environments, follow the approach in [session and environment isolation](https://facai.lol/blog/cookie-session-environment-isolation-2026): one session per environment.

## Layer two: version, client and tdata must be the same generation

tdata is the local session directory for Telegram Desktop, and the directory structure is not guaranteed compatible across major versions. Opening a tdata generated by a newer client in an older one, or opening a very old tdata in a new client, can fail to read the session and hang on loading.

1. Record the current client version. It is visible on the settings or about page.

2. Get the client only from the official channel: the desktop download page at [desktop.telegram.org](https://desktop.telegram.org/). Do not use third-party repackaged builds; a modified binary reads tdata in unpredictable ways.

3. Upgrade the client to the current official version, then retry the import using the backup directory.

4. If it still spins after upgrading, run a control test in a clean client directory: create an empty folder, place the official client there, and add only this one tdata. This rules out interference from old configuration.

**Verification action:** do not log into any other account during the control test. If the clean directory opens and the original does not, the problem is leftover configuration in the original directory, not tdata.

One point that is easy to miss at this layer: tdata stores a login state, not a password. Once a session has been revoked server-side, no client version can read it back. Use the table below to judge.

### Information block: symptom-to-action decision table

| Symptom | First suspicion | Action | How to confirm |

| --- | --- | --- | --- |

| Spins at startup, no login screen | Wrong path or nested directory | Check the working-directory/tdata level and remove the extra layer | Directory structure is visible directly |

| Login screen appears but will not load | Client version differs from tdata generation | Upgrade to the current official version and run a clean-directory control test | Clean directory opens, proving the original directory is at fault |

| Write failure or settings not saved after import | Read-only directory or insufficient permission | Check folder attributes and the current user's write permission | See the layer-three permission checklist |

| Interface opens but messages are blank | Network exit or account state | Check network and account first; do not touch tdata | Session loaded, so the file is not the problem |

| Limited functionality after switching devices | Same session used concurrently on multiple devices | Stop the extra environments and keep one session only | Depends on the account state |

## Layer three: permission, a read-only directory fails silently

This layer is the least obvious. When a directory is readable but not writable, the client can open tdata but cannot write the files it needs at runtime. The result is a permanent spin or a reset to the initial state on every launch.

1. Right-click the `tdata` folder and open properties. Confirm the read-only attribute is not checked. If it shows a filled state, clear it and apply.

2. Confirm the currently logged-in system user has write permission on the folder, not read-only access. Directories copied from another computer often carry the original machine's permission settings.

3. Check whether the folder sits on a sync drive, network drive or protected read-only partition. These locations may report writable while actually blocking writes.

4. Copy the entire `tdata` to a normal local disk directory and try again to rule out the location.

5. Confirm security software is not blocking writes to the directory. If protection software was installed recently, whitelist the folder and retest.

**Verification action:** manually create and save a text file in the same directory as `tdata`. If saving fails, the location as a whole is not writable and the problem is not tdata itself.

### Checklist: six pre-import self-checks

- The client is fully quit with no leftover process.

- The tdata level is `working-directory/tdata/...` with no same-name nesting.

- The client came from the official download page and is the current version.

- The directory is not marked read-only and the current user has write permission.

- The directory is not on a sync drive, network drive or read-only partition.

- The same session is not in use on another device at the same time.

If all six pass and it still spins, stop reinstalling the client. At that point the session itself has most likely expired server-side, and you need a fresh login to obtain a new session rather than more file repair. For handling guidance, see [the relogin flow after session expiry](https://facai.lol/blog/telegram-session-invalid-relogin-2026).

## Three things to do after a successful import

Getting past the spin and into the interface only proves the session is usable. It does not make the account secure. Complete these three steps in order before putting the account into daily use:

1. **Change the password immediately.** The first action after logging in on a new device is to change the password, so that whoever held the old session no longer has room to act.

2. **Enable Two-Step Verification.** The path is `Settings → Privacy and Security → Two-Step Verification`. Set a strong password independent of other sites, fill in a password hint that does not reveal the real answer, bind a recovery email and complete the email code confirmation, then log in once more to confirm it took effect.

3. **Clear unfamiliar devices.** The path is `Settings → Privacy and Security → Devices`. Check each entry's device name, platform and last active time, and terminate any session you do not recognize. Check the device list again after a full 24 hours, force out any unfamiliar device still online, then change the password and reset Two-Step Verification.

For accounts received through delivery, do not mass-message, do not add large numbers of friends and do not switch IPs frequently within the first 7 days. These are high-frequency triggers for risk controls. They are unrelated to whether tdata imported successfully, but they directly determine whether the account holds. Delivery and guarantee scope follow the [service directory](https://facai.lol/services) page: delivery problems within the first 24 hours of first login are handled under the replacement guarantee; anything past that window, or caused by changing the password, rebinding, resale or prohibited use, falls outside the guarantee.

If you need a complete set of session and account environments, browse the current categories in the [Telegram zone](https://facai.lol/tg-zone), or review covered platforms in the [social accounts directory](https://facai.lol/social-accounts). Specific listings and availability are shown on the page after login.

## Common mistakes that waste half the time

- **Reinstalling the client repeatedly.** Reinstalling clears the program, not the working directory. Path and permission problems remain exactly as they were.

- **Deleting the old tdata outright.** Once deleted there is no rollback. Rename it as a backup first, and clean up only after the new directory works.

- **Changing the password right after import.** Changing the password invalidates the old session immediately. If you are using that session to verify the import, you will misread it as an import failure. Confirm you can get in first, then change the password.

- **Sharing one session across devices.** Convenient in the short term, a frequent risk-control trigger in the long term.

Treat the three layers as a fixed sequence: check the directory level first, then match the version, then verify permission. Each layer has a verification action you can see or perform, so there is no need to guess. If it still fails after all three, treat it as an expired session and log in again for a new one. That saves more time than continuing to repair files.
